## Supabase diagnosis

The connected Supabase project is `perx` (`qtmvausduxiqcguckfql`), healthy in `eu-north-1`. A read-only count query on 2026-11-11 returned:

- `public."User"`: 23 records
- `public."Session"`: 29 records
- `public."PasswordResetToken"`: 15 records
- `auth.users`: 0 records

The app's current sign-in code authenticates against the Prisma `User` model and its `passwordHash`, and its cookie sessions are checked against the Prisma `Session` model. The password recovery flow issues records in `PasswordResetToken`, hashes token values before storage, expires grants after 30 minutes, and atomically consumes a token to prevent a second redemption. This is a **custom application authentication system**, not Supabase Auth.

**Do not wire `supabase.auth.resetPasswordForEmail()` into the existing password-recovery screen as a shortcut.** It would query the separate Supabase Auth user store, which currently contains zero users, and would not update `public."User".passwordHash`. Moving the existing users to Supabase Auth is a separate authentication migration and needs an explicit account migration/re-enrolment plan.

## Existing recovery-email delivery seam

The current application already routes password-reset mail through its generic email provider. In production it selects Resend only when both settings exist:

- `RESEND_API_KEY` — secret; server-side only.
- `EMAIL_FROM` — sender address/name on a sending domain verified with the email provider.

Set this canonical application origin:

- `NEXT_PUBLIC_APP_URL=https://www.ptahx.com`

The reset link is generated by the application at `/reset-password?token=...` and validated against the existing `PasswordResetToken` table. The reset form updates the existing custom-auth password hash and revokes sessions. No Supabase Auth redirect URL is needed for this existing flow.

For deliverability, verify `ptahx.com` in the email provider and publish its requested DNS records (typically SPF/DKIM; DMARC is strongly recommended). The suggested sender `no-reply@ptahx.com` is an example only; use an address permitted by the verified sender/domain. Disable click tracking for one-time password links if the provider's link rewriting interferes with token URLs. Keep the API key in Vercel's production environment only; never add it to Git, a `NEXT_PUBLIC_*` variable, or client code.

**Not completed by this PR:** no Resend account, DNS records, SMTP/API credentials, Vercel variables, Supabase Auth settings, or live email-delivery test have been changed. The project owner must supply/configure the Resend key and complete domain verification in the appropriate dashboards.

## Forgotten email versus forgotten password

The existing form supports a password reset when a person knows the email address associated with their account. It does not safely reveal or look up a forgotten email address. Treat that as a separate account-recovery/support journey: do not disclose whether a username or account exists, and do not show an account's full email address to an unverified requester.

## Supabase Auth settings — only if we later migrate authentication

If an explicit migration to Supabase Auth is approved, configure `https://www.ptahx.com` as the Site URL and add exact application callback/reset URLs to the Redirect URL allow-list. Configure a custom SMTP provider for production delivery; Supabase's built-in mail service is for limited testing and is restricted to pre-authorized addresses. Do not enable a mixed state where new users use Supabase Auth but existing users still use a separate password hash without a deliberate account-linking plan.

## First-run UX

The first authenticated visit uses the existing `User.onboardingDismissedAt` marker. The welcome panel provides:
- a clear explanation of Home, Discover, Messages, Deals and Settings;
- an immediate action to open Messages;
- an optional five-step guide with back/next, progress and links to the relevant sections;
- a persistent floating Guide entry after dismissal.

The guide is lightweight, uses the existing Radix dialog/React components and icons, respects reduced-motion settings, hides on immersive mobile conversation screens/while the software keyboard is open, and uses minimum 44px controls.

## Responsive forms

The shared Field/Input/Textarea/Select and password-input wrappers now use shrinkable width constraints. On narrow touch screens, controls are capped to their parent width and use a 16px font to avoid iOS focus zoom. The authenticated scroll container is constrained to the available width. Playwright coverage checks key app routes at 320–768px and first-run guide bounds on a 320px viewport.

## Production release gate

Before merging/deploying to production:
1. Confirm preview build and Playwright checks pass.
2. Authorize access to the Vercel team and inspect the production variable **names/targets** without exposing decrypted secrets.
3. Confirm production `NEXT_PUBLIC_APP_URL`, database configuration, `RESEND_API_KEY` and `EMAIL_FROM` are present in the correct environment.
4. Confirm `www.ptahx.com` resolves to the intended Vercel production project and TLS is valid.
5. Verify sending domain DNS records and test a complete reset with a dedicated test account; ensure the email arrives and the one-time link updates the same custom-auth account.
6. Do not change Supabase Auth users, apply a DB migration, or change the password store as part of this UX rollout.

Vercel environment-variable changes require a new deployment to take effect. No production settings or live database schema were altered by this branch.
